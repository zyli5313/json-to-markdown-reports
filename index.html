Turning API JSON into a readable report: tables for records, lists for nesting

You have a JSON response, such as test results, a list of tickets or an export from a database, and someone who doesn't read JSON needs to see it in a PR description, a status update or a wiki page. The right Markdown shape depends on the shape of the JSON, and that is where most quick conversions go wrong.

Rule 1: Flat records become a table

An array of objects that share the same keys is really a spreadsheet:

[{"id": 1, "status": "passed", "ms": 120},
 {"id": 2, "status": "failed", "ms": 980}]

That becomes a table with columns id | status | ms. Missing keys become empty cells, not shifted columns.

Rule 2: Nested data becomes an indented list

Configuration objects, trees and anything with objects inside objects doesn't fit a grid. Squashing it into a table cell ({"a":{"b":1}}) helps nobody. An indented bullet list that mirrors the nesting keeps it readable.

The JSON to Markdown converter on dochost applies exactly these two rules automatically. It escapes pipe characters, keeps nulls visible and runs in the browser, so nothing is uploaded.

Details that matter in a report

  • Nulls: show them as null or a dash. An empty cell is ambiguous: was the value missing, or empty?
  • Pipes in strings: an unescaped | breaks the table. It has to become \|.
  • Long strings: truncate stack traces and link to the full log.
  • Column order: put the identifying column first and the status second. Readers scan from the left.

Trim before you convert

Use jq to keep only the fields the reader needs, for example jq '[.[] | {id, status, duration_ms}]' results.json. A five-column table gets read. A 30-column table gets skipped.

When the audience wants a spreadsheet

Finance and ops people often want to sort and filter. Once the data is a Markdown table, Markdown to Excel turns it into a real .xlsx file they can open directly.
